# NIIRONA — кратко

**NIIRONA — локальная модульная AI-система, в которой LLM не является хозяином всей архитектуры.**

Модель отвечает за рассуждение, но управление, состояние, контекст, исполнение, тестирование, восстановление и инфраструктура моделей вынесены в отдельные подсистемы.

Главная идея:

> **не строить один огромный “умный” агент, который знает и контролирует всё.**

## Что такое NIIRONA?

NIIRONA — независимо разрабатываемая local-first AI-система, объединяющая диалог, автономное выполнение задач, детерминированное управление, проектный контекст, проверку результатов, восстановление после сбоев, сменяемые локальные/облачные LLM, голосовой интерфейс и отдельный Unity-клиент с аватаром.

LLM рассуждает, а управление исполнением, состоянием, маршрутизацией и восстановлением остаётся за детерминированными подсистемами.

Этот публичный репозиторий показывает назначение, возможности, состояние и архитектурные принципы проекта, но намеренно не содержит деталей реализации, достаточных для воспроизведения production-системы.

## Независимый проект одного разработчика

NIIRONA — независимый проект, создаваемый одним разработчиком. На текущем этапе за проектом не стоит команда, компания, инвестор или спонсор. Разработка, интеграция, тестирование и архитектурная работа ведутся самостоятельно с использованием AI-инструментов как части инженерного процесса.

---

## Что уже есть в архитектуре

- локальная работа как основной сценарий;
- поддержка локальных и облачных LLM;
- детерминированный управляющий слой;
- отдельные ветки чата и автономного исполнения;
- явная активация задач;
- отдельный Advanced Context Manager;
- отдельные подсистемы состояния, целей, знаний проекта, тестирования, confidence, sandbox и rollback;
- восстановление после перезапуска;
- изолированное исполнение;
- тестирование и evidence для попыток выполнения;
- возможность менять LLM без переделки всей системы;
- архитектура Intent Gate;
- направление LLM Runtime & Routing Manager;
- схема cloud → local teaching.

---

## Unity / аватар — уже отдельная программа

Клиентская часть NIIRONA — это уже не только будущий план.

Создана **отдельная программа на Unity**, которая работает с аватаром независимо от управляющего ядра NIIRONA.

В ней уже развивается:

- загрузка и управление аватаром;
- поиск и сопоставление костей;
- работа с rig;
- позы и движения тела;
- руки и пальцы;
- настройка нейтрального положения кистей;
- визуальное меню и интерфейс;
- подготовка к связи с чатом и голосом.

Сейчас продолжается доводка поведения кистей и пальцев и финальная интеграция Unity-клиента с основной архитектурой.

Важно: Unity-клиент не является управляющим ядром. NIIRONA может работать без аватара, а в будущем к тому же ядру можно подключать другие интерфейсы.

---

## Важный принцип

Фраза пользователя сама по себе не должна становиться командой исполнения.

Например:

> «Qwen неплохо пишет код»

не должно автоматически означать:

> «Переключись на Qwen».

Conversation Plane и Execution Plane разделены, а переход к управляющему действию проходит через контролируемое определение намерения.

---

## Модели — заменяемый ресурс

NIIRONA строится так, чтобы LLM можно было менять без перестройки всей системы.

Отдельный LLM Runtime & Routing Manager предназначен для:

- реестра моделей;
- локальных и облачных провайдеров;
- назначения GPU;
- запуска и остановки моделей;
- активной модели;
- hot-switch;
- мониторинга состояния;
- нескольких моделей одновременно;
- будущего автоматического подбора подходящей модели под доступное железо.

---

## Контекст

Advanced Context Manager отвечает за организованный контекст проекта и должен выдавать модели минимальный актуальный набор информации для конкретной задачи.

Он может учитывать:

- структуру проекта;
- зависимости;
- связанные файлы;
- тесты;
- актуальность;
- историю;
- архитектурные ограничения.

При этом ACM не управляет исполнением.

## Почему публичная схема неполная

Мы сознательно не публикуем:

- внутренние контракты;
- схемы сообщений;
- state machine;
- точные failure/recovery протоколы;
- приватные интерфейсы;
- security internals;
- production-конфигурации;
- внутренние тестовые fixtures.

Цель этого репозитория — показать уровень проекта и его архитектурное направление, не публикуя готовый чертёж для копирования.
